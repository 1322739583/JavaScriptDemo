# 解决跨域的三大主流方案（实战与工程化）

在现代前端开发中，解决跨域问题根据**开发环境**与**生产环境**有明确的最佳实践分工。

---

## 方案一：开发环境 —— 前端工程化本地代理（Vite / Webpack Proxy）

### 1. 核心原理
- **“浏览器访问服务器有跨域限制，但服务器与服务器之间通信没有跨域限制！”**
- 当你在本地运行 `npm run dev` 时，Vite 或 Webpack 实际上启动了一个**本地 Node.js 开发服务器**（例如运行在 `http://localhost:5173`）。
- 浏览器把请求发给自己的本地 Node 服务器（同源，不跨域！）；
- 本地 Node 服务器充当“中介人”，悄悄把请求转发给真正的后端服务器（`http://localhost:8080`），拿回数据再喂给浏览器。

### 2. Vite 配置示例 (`vite.config.js`)
```javascript
import { defineConfig } from 'vite';

export default defineConfig({
  server: {
    port: 5173,
    proxy: {
      // 只要请求路径以 /api 开头，就会被本地代理服务器转发
      '/api': {
        target: 'http://localhost:8080', // 真实后端接口根地址
        changeOrigin: true,              // 改变请求源的 Host 头，伪装成同源请求
        rewrite: (path) => path.replace(/^\/api/, '') // 路径重写：去掉 /api 前缀
      }
    }
  }
});
```

## 方案二：生产环境主流 —— Nginx 反向代理

### 1. 核心原理
- 在生产服务器上，通过 Nginx 监听统一的域名和端口（比如 `http://myapp.com:80`）。
- 用户访问静态页面时，Nginx 指向前端打包产物 `dist/index.html`；
- 用户调用 `/api/` 接口时，Nginx 在服务器内网将其转发到 Java/Node 后端服务（`127.0.0.1:8080`）。
- **对于用户的浏览器而言，网页和接口来自同一个域名和端口，完全同源！**

### 2. Nginx 配置模板 (`nginx.conf`)
```nginx
server {
    listen 80;
    server_name myapp.com;

    # 1. 前端打包后的静态资源
    location / {
        root /usr/share/nginx/html/dist;
        index index.html;
        try_files $uri $uri/ /index.html; # 支持 Vue Router history 模式
    }

    # 2. 后端接口反向代理
    location /api/ {
        proxy_pass http://127.0.0.1:8080/; # 转发到内网后端服务
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

## 方案三：后端配置 —— CORS（跨域资源共享）

### 1. 核心原理
- 后端在响应头中主动声明：**“我信任并允许来自该前端源的跨域请求！”**
- 浏览器在拿到响应数据后，看到合法的通行证头，就会放行把数据交给前端。

### 2. Node.js (Express) 配置示例
```javascript
const express = require('express');
const app = express();

app.use((req, res, next) => {
    // 允许任何域名访问（或指定具体域名 http://myapp.com）
    res.header("Access-Control-Allow-Origin", "*");
    // 允许客户端携带的 HTTP 方法
    res.header("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS");
    // 允许客户端携带的自定义请求头
    res.header("Access-Control-Allow-Headers", "Content-Type, Authorization");
    // 预检请求 OPTIONS 直接返回 204
    if (req.method === 'OPTIONS') {
        return res.sendStatus(204);
    }
    next();
});
```

## 方案四：经典历史方案 —— JSONP（了解即可）

- **原理**：利用 `<script src="...">` 标签不受同源策略限制的天生特权，让服务端返回一段调用前端预定义回调函数的 JS 代码（如 `callback({ id: 1, name: 'Tom' })`）。
- **致命缺点**：
  1. **只能支持 GET 请求**，无法支持 POST、PUT、DELETE；
  2. 不安全，容易遭受 XSS 跨站脚本攻击。
- **现状**：现代前端工程化中已基本全面被 CORS 和 Nginx 淘汰，面试时作为历史常识了解即可。
