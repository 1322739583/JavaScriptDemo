02_CSRF 跨站请求伪造（Cross-Site Request Forgery）

一、什么是 CSRF？

通俗比喻：【借刀杀人】。

原理：受害者在正规网站 A 登录了，浏览器存了登录 Cookie；此时受害者被诱骗打开了黑客网站 B，黑客网站 B 自动向网站 A 发起转账请求。因为浏览器发请求时会自动带上网站 A 的 Cookie，网站 A 误以为是用户本人在操作，从而执行了恶意操作！

注意：黑客其实根本拿不到、也看不到你的 Cookie，黑客只是盗用了你的身份去发请求！

二、黑客是怎么做到的？

黑客甚至不需要写复杂的 JS 代码，只需要在钓鱼页面埋一个隐藏图片或自动提交表单：

<!-- 只要用户打开黑客页面，浏览器自动向银行发起转账 GET 请求！ -->
<img src="https://bank.com/api/transfer?to=hacker&amount=1000" style="display:none;">

三、企业级实战防御四大手段：

  1. 方案一：开启 Cookie 的 SameSite 属性（最推荐、最主流）
    • SameSite=Strict：严格模式，任何第三方网站发起的请求，绝对不带 Cookie；
    • SameSite=Lax（现代 Chrome 默认值）：相对宽松，只有普通的跨站链接跳转（如点击 a 标签导航）才带 Cookie，通过 img、iframe、表单发起的跨站请求一律不带 Cookie！
  2. 方案二：CSRF Token 验证
    • 服务器给前端页面随机生成一个加密的 token 字符串（放在隐藏表单或响应头）；
    • 前端发请求时，必须在请求头（如 X-CSRF-Token）或请求体手动带上这个 token；
    • 因为黑客在第三方钓鱼网站无法跨域读取你网站上的 token，所以黑客发起的伪造请求必然缺少 token，被服务端拒绝！
  3. 方案三：验证请求来源头（Origin / Referer）
    • 服务器检查 HTTP 请求头中的 Origin 或 Referer 字段，看是不是由自己信任的合法前端域名发起的，如果发现是从 hacker.com 发过来的，直接拦截！
  4. 方案四：重要操作强制二次验证
    • 转账、改密码、删数据等高危敏感操作，弹窗要求输入短信验证码或刷脸/支付密码。
