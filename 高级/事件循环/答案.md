# 事件循环经典面试题（完整标准答案与解析）

---

# 第一部分：核心概念与原理问答（口试高频）

### 概念题 1：什么是事件循环（Event Loop）？为什么单线程的 JavaScript 需要它？

#### 【满分回答模板】
> 1. **核心定义**：事件循环是宿主环境（浏览器或 Node.js）为了协调 JavaScript 单线程执行与异步操作不阻塞而设计的一种运行时调度机制。
> 2. **为什么单线程**：JavaScript 最初作为浏览器脚本语言，核心职责是与 DOM 交互。如果设计成多线程，多个线程同时修改同一个 DOM 节点会引发复杂的互斥锁竞争、死锁与数据撕裂。因此单线程保证了 UI 状态更新的简单与可预测性。
> 3. **为什么不阻塞（怎么解决矛盾）**：单线程无法一边等待耗时任务（网络请求、定时器、用户交互）一边执行代码。因此浏览器引入了底层多线程能力（网络线程、定时器线程、GUI 交互线程）在后台等待；当异步事件就绪时，将其回调包装为任务推入任务队列；主线程调用栈空闲时，通过事件循环依次取出任务执行，从而以“单线程执行 + 外部多线程异步协作 + 事件循环调度”实现了非阻塞并发。
> 4. **行业共识**：不仅 JS，Android 的 `Looper/Handler`、iOS 的 `RunLoop`、Swing 的 `EDT` 也均采用单线程 UI + 事件/消息循环的经典架构。

### 概念题 2：前端中常见的宏任务（Macrotask）与微任务（Microtask）分别有哪些？

#### 【满分回答模板】

#### 1. 浏览器环境：
* **常见宏任务（Macrotask / Task）**：
  * **`script`（整体代码）**：这是事件循环启动时的第一个宏任务。
  * **定时器**：`setTimeout`、`setInterval`。
  * **用户交互事件（DOM Events）**：`click`、`input`、`mousemove`、`scroll` 等。
  * **网络 I/O**：`XMLHttpRequest`（Ajax）、`fetch` 数据接收完成后的回调。
  * **跨窗口/线程通信**：`MessageChannel`、`postMessage`。
* **常见微任务（Microtask）**：
  * **`Promise` 相关的状态回调**：`Promise.then()`、`.catch()`、`.finally()`。
  * **`async / await`**：`await` 语句之后挂起的后续代码。
  * **原生微任务 API**：`queueMicrotask(() => { ... })`。
  * **DOM 变动监听**：`MutationObserver`（专门监听 DOM 增删改的微任务）。

#### 2. Node.js 环境专属扩展（加分项）：
* **Node 专属微任务**：`process.nextTick`（优先级甚至高于 `Promise.then`，属于超级微任务 VIP）。
* **Node 专属宏任务**：`setImmediate`（在 Check 阶段执行）。

#### 3. 【极高频考点陷阱】（面试必问）：
* **陷阱 1：`requestAnimationFrame`（rAF）算宏任务还是微任务？**
  * **回答**：**它既不是宏任务，也不是微任务！** 它是浏览器在微任务清空之后、正式进行 UI 渲染之前的“渲染前专有钩子”，由浏览器的刷新率（通常 16.6ms）决定其执行时机。
* **陷阱 2：`new Promise(executor)` 算微任务吗？**
  * **回答**：**绝对不是！** 传入 `new Promise` 的构造函数是**纯同步执行的代码**，会立即在当前调用栈中执行，只有后面的 `.then()` 回调才是微任务！

### 概念题 3：宏任务（Macrotask）与微任务（Microtask）是如何区分的？凭什么他是宏任务，他是微任务？

#### 【满分回答模板】
> 划分的根本依据有两个维度：
> 1. **出生地与管辖权不同（最硬核依据）**：
>    * **宏任务**由**宿主环境**（浏览器/Node.js）依照 W3C/WHATWG 规范发起调度，往往需要浏览器外部线程（定时器触发线程、网络线程、操作系统输入事件）配合完成，如 `script` 整体代码、`setTimeout`、`setInterval`、I/O 操作、用户 UI 交互（click、mousemove、input 等）。
>    * **微任务**由 **JavaScript 引擎本身（如 V8）** 依照 ECMA-262 规范内部闭环发起（规范最初命名为 Job），完全在 V8 内部内存中处理，不依赖外部硬件或定时器线程，如 `Promise.then/catch/finally`、`async/await` 后续代码、`queueMicrotask`、`MutationObserver`。
> 2. **业务设计诉求不同（等得起 vs 等不起）**：
>    * 宏任务“等得起”，延迟几毫秒执行人类肉眼无感知，容忍跨线程排队。
>    * 微任务“绝对等不起”，承担的是当前执行上下文完结后的立即收尾与状态保证，必须拥有“最高优先级就地插队权”，确保在下一次 UI 渲染前统一生效，防止数据撕裂或页面视觉闪烁。

### 概念题 4：请简述单轮事件循环的完整执行时序。

#### 【满分回答模板】
> **速记口诀**：“一宏一清空，清空看渲染，循环往下走”
> 1. 从宏任务队列取出**一个**就绪的宏任务（最初为全局 `script` 脚本）压入调用栈同步执行。
> 2. 该宏任务所有同步代码执行完毕，调用栈彻底被清空。
> 3. 检查微任务队列，**一口气清空当前队列中所有的微任务**（若微任务执行中又产生了新微任务，也会在当轮全部执行完毕）。
> 4. 检查是否达到屏幕刷新间隔（如 16.6ms），若需要则由 GUI 渲染线程介入进行 UI 渲染（Style -> Layout -> Paint）。
> 5. 从宏任务队列中取出**下一个**宏任务，重复上述步骤，循环往复。

### 概念题 5：`async / await` 是宏任务还是微任务？为什么它“等不起”？

#### 【满分回答模板】
> 1. **本质归属**：`async/await` 本质是 `Promise + Generator`（协程）的语法糖。`await foo()` 右侧的 `foo()` 会立即同步执行；而 `await` 下方的代码在底层等价于包裹在 `Promise.resolve(foo()).then(() => { ... })` 的回调中，因此天然属于微任务。
> 2. **为什么等不起**：
>    * **保持同步书写的心智模型**：开发者使用 `await` 就是希望前一步完成、下一步紧接着恢复执行，绝不能被无故割裂。
>    * **防止状态被偷（防竞态）**：如果它被排为宏任务，排队期间其他定时器或用户点击可能会篡改全局状态，导致上下文失效。微任务保证了一旦等待结束，第一时间恢复调用栈，不给其他宏任务插足捣乱的机会。
>    * **避免页面撕裂闪烁**：微任务能保证在浏览器下一次渲染屏幕之前把数据计算赋值完毕，用户看到的是一次性呈现的最终画面。

### 概念题 6：事件循环与浏览器 UI 渲染（Render）的时机是什么关系？

#### 【满分回答模板】
> 1. **不是每轮微任务清空都会触发渲染**：屏幕通常以 60Hz 刷新（约 16.6ms 一帧）。如果当前宏任务 + 微任务只执行了 2ms，由于还没到达垂直同步信号（V-Sync），浏览器会跳过渲染直接执行下一个宏任务。只有到达渲染时间窗口时才会触发。
> 2. **`requestAnimationFrame`（rAF）的时机**：它不是宏任务也不是微任务，而是“渲染前钩子”。它必然发生在**微任务清空之后、浏览器正式计算样式和布局之前**执行。
> 3. **宏任务递归 vs 微任务递归的卡死差异**：
>    * `setTimeout(loop, 0)` 递归不会卡死页面：因为每执行一个宏任务，浏览器都可以喘口气清空微任务并执行 UI 渲染，用户依旧可以点击和滚动。
>    * `Promise.resolve().then(loop)` 递归会彻底让页面假死崩溃：因为微任务拥有清空铁律，不断塞入微任务导致队列永远无法清空，主线程被彻底锁死，浏览器永远无法进入渲染阶段！

### 概念题 7：Node.js 的事件循环与浏览器的事件循环有什么区别？

#### 【满分回答模板】
> 1. **底层实现**：浏览器由厂商依照 HTML/W3C 规范实现；Node.js 基于跨平台异步 I/O 库 **`libuv`** 实现。
> 2. **执行阶段划分**：Node.js 划分了 6 个明确的执行阶段，最核心的有：
>    * **Timers 阶段**：处理 `setTimeout / setInterval` 回调；
>    * **Poll 轮询阶段**：等待并处理系统网络 I/O、文件读写回调；
>    * **Check 阶段**：专门执行 `setImmediate` 回调。
> 3. **专属特权 API**：
>    * **`process.nextTick`**：独立于事件循环之外的超级微任务，其优先级甚至高于 `Promise.then`，在每个阶段切换前最优先插队清空！
>    * **`setImmediate`**：Node.js 专属宏任务，在 Check 阶段执行。
>    *(注：Node 11 之后，Node 在执行宏任务时的微任务调度已经与浏览器统一为“一宏一清空”)*。

# 第二部分：代码输出顺序推演（笔试必考）

## 题目一：辨别 Promise 的同步执行与微任务（基础必考）

### 1. 题目代码

```javascript
console.log('1');

setTimeout(() => {
  console.log('2');
}, 0);

new Promise((resolve) => {
  console.log('3');
  resolve();
  console.log('4');
}).then(() => {
  console.log('5');
});

console.log('6');
```

### 2. 输出结果

```text
1
3
4
6
5
2
```

### 3. 常见易错分析（高频避坑）

* **常见错误答案**：`1 6 2 3 4 5` 或 `1 6 5 2 3 4`
* **易错点 1（致命陷阱）**：误以为只要写了 `new Promise(...)`，里面所有代码都会延后异步执行。
  * **正解**：传给 `new Promise(executor)` 的回调函数叫**执行器**，当 V8 引擎读到这一行时，是**立即、同步在当前调用栈中执行**的！
  * 只有后面的 `.then()` / `.catch()` 里的回调函数，才会被放入**微任务队列**。
* **易错点 2**：误以为 `setTimeout` 哪怕是 0 毫秒也会比 `.then()` 先执行。
  * **正解**：`setTimeout` 是**宏任务**，`.then()` 是**微任务**。单轮事件循环中，同步代码执行完后，必须**先清空所有微任务**，才会轮到下一个宏任务。

### 4. 逐行执行流程（慢动作推演）

1. **执行第 1 行**：`console.log('1')` 属于同步任务，直接压入调用栈并执行，**输出 `1`**。
2. **执行第 3 行**：遇到 `setTimeout`，交由浏览器的定时器线程处理，回调函数注册进入**宏任务队列**。
3. **执行第 7 行**：遇到 `new Promise(...)`，**立即同步执行其内部的构造函数逻辑**：
   * 打印 `3`，**输出 `3`**；
   * 调用 `resolve()`，标记 Promise 状态为成功，并将 `.then` 里的回调函数推入**微任务队列**；
   * 打印 `4`，**输出 `4`**。
4. **执行第 15 行**：`console.log('6')` 属于同步任务，直接执行，**输出 `6`**。
   * *(至此，第一轮宏任务的所有同步代码执行完毕，当前输出为：`1, 3, 4, 6`，调用栈为空)*
5. **清空微任务队列**：
   * 事件循环检查微任务队列，取出排队的 `.then` 回调并执行，打印 `5`，**输出 `5`**。
6. **执行下一轮宏任务**：
   * 微任务已全部清空，事件循环从宏任务队列中取出就绪的 `setTimeout` 回调并执行，打印 `2`，**输出 `2`**。

## 题目二：`async / await` 与 `Promise` 的交织（进阶高频）

### 1. 题目代码

```javascript
async function async1() {
  console.log('1');
  await async2();
  console.log('2');
}

async function async2() {
  console.log('3');
}

console.log('4');

setTimeout(() => {
  console.log('5');
}, 0);

async1();

new Promise((resolve) => {
  console.log('6');
  resolve();
}).then(() => {
  console.log('7');
});

console.log('8');
```

### 2. 输出结果

```text
4
1
3
6
8
2
7
5
```

### 3. 核心解题心法（两把金钥匙）

1. **`await` 右侧的函数是【立即同步执行】的！**
   * 很多人以为遇到 `await` 整个函数就挂起了。其实不是，`await async2()` 会**立即同步跑进 `async2` 内部**，所以 `3` 紧跟着 `1` 立即同步打印出来。
2. **`await` 下方的代码被打包进【微任务队列】！**
   * `async2()` 执行完毕后，`await` 下面的 `console.log('2')` 相当于放进了 `Promise.then` 里面，推入**微任务队列（排名第一）**。
3. **微任务队列严格遵守【先进先出（FIFO）】**：
   * `async1` 里的 `2` 先进入微任务队列；
   * 后面的 `new Promise.then` 里的 `7` 后进入微任务队列；
   * 所以在清空微任务时，一定是 **先输出 2，再输出 7**！

### 4. 逐行执行流程（慢动作推演）

1. **执行第 11 行**：同步代码直接打印 `4`，**输出 `4`**。
2. **执行第 13 行**：遇到 `setTimeout`，交由定时器线程，回调登记进入**宏任务队列**。
3. **执行第 17 行**：调用 `async1()`：
   * 同步打印 `1`，**输出 `1`**；
   * 遇到 `await async2()`，**立即同步调用 `async2()`**；
   * 进入 `async2`，同步打印 `3`，**输出 `3`**；
   * `async2` 执行完毕返回 Promise，`await` 下方的 `console.log('2')` 被推入**微任务队列（任务 1）**；
   * 让出主线程，跳出 `async1`。
4. **执行第 19 行**：遇到 `new Promise(...)`，执行器立即同步执行，打印 `6`，**输出 `6`**；
   * 调用 `resolve()`，将 `.then` 里的回调函数推入**微任务队列（任务 2）**。
5. **执行第 28 行**：同步代码直接打印 `8`，**输出 `8`**。
   * *(至此，同步阶段全部结束，已输出：`4, 1, 3, 6, 8`)*
6. **清空微任务队列（按入队顺序 FIFO 依次执行）**：
   * 取出任务 1（`await` 后续代码），打印 `2`，**输出 `2`**；
   * 取出任务 2（Promise `.then` 回调），打印 `7`，**输出 `7`**。
7. **执行宏任务队列**：
   * 取出 `setTimeout` 回调，打印 `5`，**输出 `5`**。

## 题目三：宏任务与微任务的嵌套循环（大厂真题）

### 1. 题目代码

```javascript
console.log('1');

setTimeout(() => {
  console.log('2');
  Promise.resolve().then(() => {
    console.log('3');
  });
}, 0);

new Promise((resolve) => {
  console.log('4');
  resolve();
}).then(() => {
  console.log('5');
  setTimeout(() => {
    console.log('6');
  }, 0);
});

console.log('7');
```

### 2. 输出结果

```text
1
4
7
5
2
3
6
```

### 3. 核心解题心法（“一宏一清空”的极致体现）

* **易错点**：很多人以为宏任务 `2` 打印完后，紧接着会打印宏任务 `6`。
* **铁律法则**：
  * **每执行完【一个】宏任务，主线程必须立即停下来，把当前新产生的微任务全部清空，然后才能取出下一个宏任务！**
  * 当执行宏任务 `setTimeout(2)` 时，内部产生了微任务 `3`。
  * 所以 `2` 执行完毕后，**必须立刻去执行微任务 `3`**，最后才轮到之前排队的另一个宏任务 `6`！

### 4. 逐行执行流程（慢动作推演）

1. **第一轮宏任务（主线程初始同步代码）**：
   * 打印 `1`，**输出 `1`**；
   * 遇到定时器 1，注册进入宏任务队列 `[定时器 1(包含 2 和 3)]`；
   * 遇到 `new Promise(...)`，执行器立即同步执行，打印 `4`，**输出 `4`**，`resolve()` 将 `.then` 放入微任务队列 `[微任务 1(包含 5 和 6)]`；
   * 打印 `7`，**输出 `7`**。
   * *(主线程同步结束，输出：`1, 4, 7`)*

2. **清空第一轮微任务**：
   * 取出 `微任务 1` 执行：打印 `5`，**输出 `5`**；
   * 遇到内部的 `setTimeout`，注册进入宏任务队列，此时宏任务队列为：`[定时器 1, 定时器 2(包含 6)]`。
   * 微任务队列清空。*(当前总输出：`1, 4, 7, 5`)*

3. **进入第二轮宏任务**：
   * 从宏任务队列取出队头任务：`定时器 1` 执行；
   * 打印 `2`，**输出 `2`**；
   * 遇到 `Promise.resolve().then(...)`，产生新的微任务，推入微任务队列 `[微任务 2(包含 3)]`。
   * 该宏任务执行完毕。

4. **立即清空第二轮新产生的微任务（关键插队！）**：
   * 事件循环检查微任务队列，发现刚才新增的 `微任务 2`；
   * 立即取出执行，打印 `3`，**输出 `3`**。
   * *(当前总输出：`1, 4, 7, 5, 2, 3`)*

5. **进入第三轮宏任务**：
   * 微任务已清空，取出宏任务队列中剩下的 `定时器 2` 执行；
   * 打印 `6`，**输出 `6`**。
   * *(所有队列彻底清空，最终输出：`1, 4, 7, 5, 2, 3, 6`)*
