# 浏览器缓存机制与现代前端工程化实践

## 一、 核心概念与决策流程树

浏览器缓存（HTTP Cache）是提升 Web 性能、降低服务器带宽消耗的最关键支柱。按控制优先级划分为两层：**强缓存** 与 **协商缓存**。

### 决策流程树（浏览器请求静态资源时的完整链路）

```text
[浏览器发起资源请求]
         │
         ▼
[1. 检查强缓存 (Cache-Control / Expires)]
   ├── 没过期且未配置 no-cache：
   │     └── 直接命中强缓存！返回 200 (from memory cache / from disk cache)
   │         【0毫秒、0网络消耗，不向服务器发送任何请求】
   │
   └── 已过期 或 响应头配置了 no-cache：
         └── 携带上一次记录的暗号 (ETag / Last-Modified)，向服务器发起请求
                 │
                 ▼
[2. 服务器核对协商缓存]
   ├── 服务器核对指纹/时间，确认文件【未被修改】：
   │     └── 返回状态码【304 Not Modified】（不携带 Body 响应体，仅几个字节）
   │         告诉浏览器直接使用本地已缓存的文件！
   │
   └── 服务器核对发现文件【已被修改】：
         └── 返回状态码【200 OK】，并把最新的文件内容完整下发给浏览器！
```

## 二、 核心 Header 字段全解析

### 1. 强缓存（本地决策）

| 字段 | HTTP 版本 | 典型值 | 作用与含义 | 优先级 |
| :--- | :--- | :--- | :--- | :--- |
| **`Cache-Control`** | HTTP 1.1 | `max-age=31536000` | 相对时间（秒）。表示资源在客户端自请求起 1 年内都有效。 | **高**（现代标准，绝对主力） |
| **`Expires`** | HTTP 1.0 | `Wed, 21 Oct 2026 07:28:00 GMT` | 绝对时间戳。由于依赖客户端系统时间，改时间即失效，已被淘汰。 | **低**（被 Cache-Control 覆盖） |

#### `Cache-Control` 最核心指令辨析（面试极高频陷阱）
* **`no-cache`**：**并不是“不缓存”！** 它的真实含义是**“跳过本地强缓存，每次都必须向服务器发起协商缓存确认文件是否改动”**。
* **`no-store`**：**才是真正的“彻底不存任何缓存”**。任何时候都必须重新从服务器全量下载。
* **`public`**：客户端和所有中间代理服务器（如 CDN、网关）都可以缓存。
* **`private`**：仅允许终端用户的浏览器本地缓存，不允许 CDN 等共享代理缓存。

---

### 2. 协商缓存（与服务器对暗号）

协商缓存由服务器与客户端成对使用的两对 Header 控制：

| 校验维度 | 响应头（服务器发给客户端） | 请求头（客户端下次带给服务器） | 优缺点与特点 | 优先级 |
| :--- | :--- | :--- | :--- | :--- |
| **文件内容哈希** | **`ETag`**<br>`"a8f9c1-654"` | **`If-None-Match`**<br>`"a8f9c1-654"` | **精准度极高**。只要文件内容没变，哪怕修改时间变了也算命中；精度达到微秒级。 | **最高**（优先比对） |
| **最后修改时间** | **`Last-Modified`**<br>`2026-10-19 12:00:00` | **`If-Modified-Since`**<br>`2026-10-19 12:00:00` | **秒级精度**。如果 1 秒内文件改了多次无法感知；如果只打开保存但没改内容，时间变了会导致缓存失效。 | **次高**（备用辅助） |

### 3. 深度概念辨析：为什么叫“协商”？英文真名叫什么？（破除中式翻译误区）

很多开发者觉得“协商”这个词很怪——中文里“协商”意味着两个人坐下来**讨价还价、商量妥协**，但计算机之间根本没有妥协，只有非黑即白的确认。

这其实是一个**历史遗留的“中式翻译大烂锅”**：
1. **RFC 官方规范中的真名**：
   * 在 IETF / W3C 的 HTTP 规范（RFC 7234 / RFC 9111）中，**根本没有“Negotiation Cache（协商缓存）”这个词**！
   * 官方标准行为学名叫：**`Cache Revalidation`（缓存重新验证 / 缓存核验）**。
   * 发出的请求学名叫：**`Conditional Requests`（条件请求）**（携带 `If-None-Match`、`If-Modified-Since` 条件）。
2. **“协商”二字从何而来？**
   * HTTP 协议中确实有一个机制叫 **`Content Negotiation`（内容协商）**，用于客户端和服务端商量语言、压缩格式（`Accept-Language`、`Accept-Encoding`）。
   * 国内早期翻译者和教程把“内容协商”的概念**张冠李戴**扣在了“缓存重新验证”头上，后来大家口口相传、约定俗成变成了“协商缓存”。
3. **最接地气的理解**：
   * **不要把它当成“协商”，它本质上就是【核验缓存】或者【对账缓存】！**
   * 拿着你手里的发票/哈希，去跟服务器对一次账。账目对得上（没改），回 304 继续用；账目对不上（改了），回 200 领新的。

## 三、 现代前端工程化黄金缓存方案（ContentHash + 动静分离）

### 1. 为什么不能一刀切开强缓存？
* 全部开强缓存 -> 代码上线更新，用户本地读旧代码，造成重大线上 Bug；
* 全部不开强缓存 -> 每次访问几兆的 JS/CSS 重新下载，首屏卡顿、带宽浪费。

### 2. 工业级最佳配置实践

```text
 dist/
   ├── index.html                    --> 【走协商缓存】：Cache-Control: no-cache
   └── assets/
         ├── vendor.a8f9c1.js        --> 【走 1 年强缓存】：Cache-Control: max-age=31536000
         └── app.3b4d2e.js           --> 【走 1 年强缓存】：Cache-Control: max-age=31536000
```

* **`index.html`（网站导航仪/钥匙串）**：
  * 体积通常仅 1~2KB；
  * 配置 `Cache-Control: no-cache`；
  * 保证用户每次刷新都向服务器核对拿到**最新的入口 HTML**。
* **静态资源（JS / CSS / 图片 / 字体）**：
  * 通过 Vite / Webpack 配置 `[name].[contenthash].js`；
  * 配置 `Cache-Control: max-age=31536000`（缓存 1 年）；
  * 没发版时：0 毫秒从本地磁盘秒开；
  * 改代码发版后：内容变导致 Hash 变（文件名变了！），旧缓存不冲突，浏览器自动向服务器下载全新文件！

## 四、 深度进阶：依赖树哈希连锁反应与 ChunkLoadError

### 1. 为什么懒加载子组件没写在 `index.html` 也能拿到最新 Hash？
* 依赖链条：`index.html` -> `main.[hash].js` -> `import('./User.[hash].js')`。
* 当你只改动了 `User.vue` 时：
  1. `User` 的 Hash 改变（生成新文件）；
  2. `main.js` 内部记载的动态引用路径发生变更 -> 导致 `main.js` 内容发生变动；
  3. `main.js` 的 Hash 跟着改变；
  4. 打包工具自动将最新的 `main.[newHash].js` 写入 `index.html`；
  5. 浏览器拿到最新 HTML -> 加载最新 main -> 顺着 main 加载最新子路由。

### 2. 经典线上事故：`Loading chunk failed`
* **事故成因**：用户停留在旧页面未刷新，内存中运行着旧 `main.js`；此时服务器发版清理了旧文件。用户在页面内点击跳转路由时，旧 `main.js` 试图请求已不存在的旧 Hash chunk，导致 404！
* **解决方案**：在前端路由全局错误中捕获并自动强制刷新页面：
  ```javascript
  router.onError((error) => {
    if (/Loading chunk.*failed/.test(error.message)) {
      window.location.reload();
    }
  });
  ```
