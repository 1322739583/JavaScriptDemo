# 浏览器缓存经典面试题（完整标准答案与解析）

### 题目一：请谈谈你对浏览器缓存机制的理解，强缓存和协商缓存有什么区别？

#### 【满分回答模板】
> 浏览器缓存是 HTTP 性能优化的核心手段，整体遵循**“先强缓存、后协商缓存”**的两层决策树：
> 
> 1. **第一阶段（强缓存）**：
>    * 浏览器发起请求前，先检查本地缓存中的响应头。
>    * 如果处于有效期内（主要看 `Cache-Control: max-age`，HTTP 1.0 看 `Expires`），且没有配置 `no-cache`：
>    * 浏览器**根本不向服务器发送任何请求**，直接从本地内存（memory cache）或磁盘（disk cache）读取资源，返回状态码 **`200 (from memory/disk cache)`**，耗时为 0 毫秒。
> 2. **第二阶段（协商缓存）**：
>    * 如果强缓存已过期、或者显式声明了 `Cache-Control: no-cache`：
>    * 浏览器会带上缓存标识（`If-None-Match: ETag` 或 `If-Modified-Since: 时间戳`）向服务器发起一次网络请求，询问文件是否改动。
>    * **若服务器比对发现文件未改动**：返回状态码 **`304 Not Modified`**，响应报文**不带 Body 内容**（体积极小），告诉浏览器继续安全使用本地旧缓存。
>    * **若服务器比对发现文件已改动**：返回状态码 **`200 OK`**，并下发最新的完整文件内容和新的缓存标识。
> 
> **一句话总结区别**：强缓存“完全不跑网络，直接读本地”；协商缓存“跑一趟网络对暗号，没变回 304，变了下发 200”。
> 
> #### 【加分拓展：为什么叫“协商”？（破除中式翻译，展示规范深度）】
> * 很多开发者觉得“协商”听起来像讨价还价。其实在 **HTTP 官方 RFC 规范（RFC 7234 / RFC 9111）** 中，**根本没有“Negotiation Cache”这个词**！
> * 官方标准学名叫 **`Cache Revalidation`（缓存重新验证 / 缓存核验）**，发出的请求叫 **`Conditional Requests`（条件请求）**。
> * “协商”二字纯属国内早期把“内容协商（Content Negotiation）”张冠李戴搞混的翻译遗留。本质就是一次非黑即白的**“带条件对账核验”**！面试时顺带点出这一点，能极大地体现对官方 RFC 规范的扎实理解。

### 题目二：`Cache-Control` 中的 `no-cache` 和 `no-store` 有什么区别？

#### 【满分回答模板】
> 这是面试中最容易被字面意思误导的高频考点：
> 
> 1. **`no-cache` 绝对不是“不缓存”**：
>    * 它的真实含义是：**“跳过本地强缓存验证，每次使用该资源前，都必须向服务器发起协商缓存确认文件是否改动”**。
>    * 本地依然会把文件存下来，只是每次用之前都要发请求拿一个 304 才能用。
> 2. **`no-store` 才是真正的“彻底不存任何缓存”**：
>    * 浏览器与中间代理服务器（CDN）**严禁将该资源写入任何本地磁盘或内存**。
>    * 每次请求都必须当成第一次全新访问，百分之百从服务器全量下载。
> 
> **典型业务场景**：
> * 前端单页应用的入口 `index.html` 适合配置 `no-cache`（每次向服务器确认是否发了新版本）；
> * 涉及银行交易、个人敏感隐私数据、绝密财务报表的接口响应，适合配置 `no-store`（绝不在本地留痕）。

### 题目三：协商缓存中，既然已经有了 `Last-Modified`，为什么还要引入 `ETag`？

#### 【满分回答模板】
> `Last-Modified` 是基于文件的“最后修改时间戳”进行判断的，在复杂的工业级场景下存在 **三大无法解决的缺陷**：
> 
> 1. **时间精度不足（秒级盲区）**：
>    * `Last-Modified` 只能精确到**秒级**。如果某个文件在 1 秒内被高频修改了多次（例如 100 毫秒改了一次），时间戳没有变化，服务器就会误以为文件没变，错误返回 304，导致客户端漏掉更新。
> 2. **假修改导致缓存击穿**：
>    * 某些服务器定期执行脚本打开了文件但没改动任何内容并重新保存，或者服务器代码重新解压部署，导致文件的修改时间改变了。此时虽然内容完全一致，但 `Last-Modified` 变了，导致浏览器重新全量下载无意义的数据。
> 3. **分布式服务器集群不同步**：
>    * 在多台服务器组成的集群中，不同机器上的同一文件由于部署时间或时钟差异，其修改时间可能不一致。用户请求打到 A 机器是 304，打到 B 机器就变成了 200。
> 
> **`ETag` 的降维打击优势**：
> * `ETag` 是根据**文件真实内容计算出的唯一哈希指纹（Hash）**。
> * 只要文件内容没变，无论时间怎么改、机器怎么换，`ETag` 绝对一致；一旦改动一个字符，`ETag` 立刻改变。因此精度与可靠性远超 `Last-Modified`（二者同时存在时，服务器优先比对 `ETag`）。

### 题目四：在实际工程中，到底开不开强缓存？你们团队是如何设计静态资源缓存策略的？

#### 【满分回答模板】
> **直接结论**：**“必须开，而且静态资源直接开 1 年强缓存！核心采用‘动静分离 + 内容 Hash’的组合拳方案。”**
> 
> 如果一刀切开强缓存，发版会导致用户读旧代码出 Bug；如果不开，用户每次访问都要重新下载几兆的 JS/CSS，不仅首屏加载慢，还浪费大量服务器 CDN 带宽。
> 
> 现代化工程的最佳实践是：
> 
> 1. **针对 `index.html`（入口导航仪 / 钥匙串）**：
>    * 配置：`Cache-Control: no-cache`。
>    * 原因：HTML 文件体积极小（仅 1~2KB）。让它每次都走协商缓存，确保用户每次刷新页面时，都能以极小的网络开销拿到**最新版本的资源入口名单**。
> 2. **针对静态资源（JS / CSS / 图片 / 字体）**：
>    * 通过打包工具（Vite / Webpack）配置文件名带上内容哈希：`[name].[contenthash].js`。
>    * 服务器配置：`Cache-Control: max-age=31536000`（开启 1 年超长强缓存）。
>    * **发版更新原理**：
>      * 没发版时：所有静态资源命中强缓存，0 毫秒从磁盘读取，极速秒开。
>      * 发版修改代码后：打包工具自动重新计算文件 Hash，**生成了全新的文件名**（如 `app.999xxx.js`）。此时最新的 `index.html` 指向新文件名，浏览器本地没有该新文件，自动下载最新资源；而未被改动的第三方库继续吃强缓存。
> 
> **一句话总结**：**“HTML 走协商拿最新钥匙，静态资源带 Hash 吃 1 年强缓存秒开，两全其美！”**

### 题目五：【线上真实事故排查】用户在页面没有刷新的情况下，系统发布了新版本，用户在页面内点击跳转路由报错 `ChunkLoadError: Loading chunk failed`，页面空白。请分析原因并给出解决方案。

#### 【满分回答模板】
> #### 1. 事故根因剖析：
> * 现代前端单页应用（SPA）普遍采用**路由懒加载（代码分割 Code Splitting）**，各个页面组件会被切分成独立的 Chunk 文件（如 `User.a1b2.js`）。
> * 当用户打开网页停留较长时间时，浏览器内存中运行的是**旧版本的 `main.js`**，里面记录的是旧的文件名映射表。
> * 此时运维发布了新版本，清除了服务器上旧版本的静态文件，换上了带新 Hash 的文件（如 `User.c3d4.js`）。
> * 用户没有刷新页面，直接在页面内点击跳转路由，旧的 `main.js` 尝试向服务器请求已经不存在的旧文件 `User.a1b2.js`，服务器返回 404，导致抛出 `ChunkLoadError: Loading chunk failed`，组件无法加载造成页面白屏。
> 
> #### 2. 解决方案：
> * **方案一（前端路由全局异常自愈）**：
>   在 Vue Router 的 `onError` 钩子中拦截捕获该错误，自动为用户强制刷新当前页面，以拉取最新的 `index.html`：
>   ```javascript
>   router.onError((error) => {
>     const pattern = /Loading chunk.*failed/g;
>     const isChunkLoadFailed = error.message.match(pattern);
>     if (isChunkLoadFailed) {
>       // 避免无限死循环刷新，可结合 sessionStorage 记录刷新次数
>       window.location.reload();
>     }
>   });
>   ```
> * **方案二（Nginx / CI/CD 运维版本留存）**：
>   服务器部署新版本时，**不要立即全量删除上一版本的静态资源目录**，保留最近 2~3 个版本的静态文件在服务器或 CDN 上（增量发布），给在线停留的旧版本用户留出缓冲期。
